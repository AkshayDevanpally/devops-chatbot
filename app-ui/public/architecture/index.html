Everything that runs on the home server today: the k3s cluster and its namespaces, Docker and the local registry, the Jenkins pipeline with Trivy, the network rules between every piece, and the planned link from AWS.

3 · Network rules: deny everything, then allow a few paths

Every namespace starts with a default-deny NetworkPolicy for traffic in and out, plus DNS. These are the only other paths that exist.

Blocked, and tested on every deploy by make verify
  • A random pod reaching Postgres, Ollama, Prometheus or the internet
  • Anyone but Prometheus reading the API's metrics port :9100
  • A privileged pod (rejected by Pod Security Admission)
  • TLS 1.1 and plain HTTP (plain HTTP gets a 301 instead)

ci and cert-manager own rules

  • Jenkins: in from Traefik on :8080 only; out on :22 and :443 (GitHub, plugins)
  • cert-manager: default deny; out to DNS and the API server only; its webhook takes :10250 from the API server
  • Known gap: k3s applies egress rules a few seconds after a pod starts. Cilium or Calico would close it.

4 · CI/CD: from git push to prod

The Jenkins controller runs in k3s; the build itself runs on the host through the agent, because it needs Docker. One image, tagged with the commit SHA, moves through dev, qa and prod.

Trivy two jobs

  • Scan: --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1. Only problems with a fix available fail the build.
  • SBOM: an SPDX JSON file per image, kept with the build.
  • In CI a missing Trivy fails the build; locally it only warns.
  • The Jenkins controller image is scanned too (ci/jenkins/.trivyignore).

Images build once

  • chat-api: Python 3.12 slim, multi-stage, uid 10001
  • ui: nginx unprivileged, uid 101; build also reads docs/ for the Error Journal page
  • OCI labels carry the git SHA; --pull gets base-image fixes every build

5 · Security layers

Each layer assumes the one above it can fail.

Host Ubuntu

  • AppArmor profile k8s-chatbot: no mounts, no writes to /proc
  • k3s protect-kernel-defaults
  • API audit log, 7 days
  • Agent is a no-login system user

Cluster k3s

  • Secrets encrypted at rest
  • kubeconfig mode 0600
  • Pipeline token limited to 3 namespaces
  • Prometheus discovery limited to the app namespaces

Pods PSA restricted

  • Non-root, read-only root filesystem
  • All capabilities dropped, no privilege escalation
  • seccomp RuntimeDefault, no service-account token
  • Requests and limits, quota per namespace

Network zero trust

  • Default deny in and out everywhere
  • Allow rules match namespace and pod label
  • Registry and API bound to localhost
  • Prometheus is not on the ingress

TLS local CA

  • cert-manager, ECDSA P-256
  • CA key never leaves the cluster
  • HTTP → HTTPS 301, HSTS, TLS 1.1 refused
  • Secure, HttpOnly, signed cookies

Data and app chat-api

  • One database and one login per environment
  • Limits enforced by DB triggers
  • Nightly backups, restore-tested weekly
  • Rate limits, CSP, input validation
  • Logs don't contain message text

8 · Next: AWS burst, database stays home

Decided on 5 Nov 2026: no RDS. When prod needs more than its 3 local API pods, Terraform creates burst compute in AWS. Those pods use the home Postgres through a tunnel, and everything in AWS is destroyed when load drops.
