QwenOps Architecture

Everything that runs today: the Raspberry Pi gateway in front of the home server, the k3s cluster and every service in it, the addresses and ports each piece uses, how a request travels, how the server sleeps and wakes, the delivery pipeline with its live page, backups, phone alerts, and the AWS capacity that exists only when it's needed.

1 · Overview map

Two machines at home and AWS only when needed. The Raspberry Pi is always on and answers for the site names; the home server runs everything else and sleeps when nobody uses it. Inside the server, k3s runs the apps and the shared platform; Docker, the build agent and the sleep and tunnel tools run on the host.

3 · A chat, end to end

What happens when someone on the home Wi-Fi sends a message to prod.

  1. Name lookup. The phone asks the network for chatbot.local; the Pi answers 192.168.1.104 (mDNS). The server itself uses its hosts file instead.
  2. Pi. nginx (stream mode) opens a TCP connection to 192.168.1.101:443 and copies bytes both ways. If the server doesn't answer within 1 second it is probably asleep, and nginx uses its backup instead: the waking page (section 4).
  3. Traefik. Ends TLS with the certificate cert-manager issued from the home CA, adds HSTS, and routes by host name: chatbot.local to prod, qa. to qa, dev. to dev. Paths under /api go to chat-api, everything else to nginx.
  4. chat-api. Gives the visitor a signed, HttpOnly uid cookie, applies rate limits, then asks the ModelGate for the model. Each pod streams one reply at a time; up to 2 people (4 in prod) wait up to 30 s and see "you're in line". When the line is full the answer is "Busy right now… try again" (503) at once.
  5. Model and data. chat-api streams the prompt to Ollama (ai, :11434) and saves the chat in its own database (chat_prod, :5432, TLS). Triggers in the database keep the latest 50 users (a new user replaces the first one created, with their chats) and each user's newest 15 chats.
  6. Dashboards. Pulse and Capacity call /api/pulse and /api/capacity; chat-api runs fixed Prometheus queries, never one from the browser. The backups panel and the Pipeline page go through backup-ops and pipeline-events in the same way.
  7. Bursting. While an AWS burst node is up, burst chat-api pods carry the same label, so the prod Service also sends requests to them over the tunnel. They use their own Ollama on AWS and the home Postgres through 10.200.0.1.

4 · Sleep and wake

The server sleeps after 30 idle minutes and wakes when someone opens the site, at 07:50 IST for the morning backups, or from a Wake-on-LAN app. The Pi makes this invisible to visitors and raises the alarm if the server goes down without saying so.

What keeps it awake idle check

  • Any app traffic in 30 min: chats, Pulse, any /api call
  • A Jenkins build, a backup job, an AWS burst node
  • An SSH session (VS Code Remote counts)
  • make stay-awake until make allow-sleep
  • 07:45–10:00 IST: backup window

Ways to wake it Wake-on-LAN

  • Open any site name: the Pi sends the magic packet
  • Its own clock alarm at 07:50 IST (backup at 08:00)
  • A Wake-on-LAN phone app (broadcast 192.168.1.255, port 9)
  • BIOS: Wake on LAN = LAN Only, Deep Sleep off

Pi alerts urgent

  • "Server is down (not asleep)": 3 min without an answer
  • "Didn't wake on schedule": 10 min after the planned wake
  • "Didn't wake after a visit": 5 min after the packet
  • "Server is back" when it answers again
  • make pi-quiet MINUTES=30 before planned work

Blocked, and tested on every deploy by make verify
  • A random pod reaching Postgres, Ollama, Prometheus or the internet

  • A privileged pod (rejected by Pod Security Admission)
  • TLS 1.1 and plain HTTP (plain HTTP gets a 301 instead)
  • One environment's login opening another environment's database

  • wg0: ufw rules allow only what the burst node needs (make burst-prepare)
  • Known gap: k3s applies egress rules a few seconds after a pod starts. Cilium or Calico would close it.

6 · Delivery pipeline: from git push to prod

The Jenkins controller runs in k3s; the build itself runs on the host through the agent, because it needs Docker. One image, tagged with the commit SHA, moves through dev, qa and prod.

Trivy two jobs

  • Scan: --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1. Only problems with a fix available fail the build.
  • SBOM: an SPDX JSON file per image, kept with the build.
  • The Jenkins controller image is scanned too, and takes Debian updates when built.

Images build once

  • chat-api: Python slim, multi-stage, uid 10001
  • ui: nginx unprivileged, uid 101; the build also reads docs/ for the Error Journal page
  • Jenkins: 2.580.2 LTS with plugins baked in
  • OCI labels carry the git SHA; --pull gets base-image fixes every build

8 · Backups

Postgres is the only data. It is backed up every morning on the server, restored as a test every Sunday, and copied to S3 every three days. The server wakes itself at 07:50 IST so the jobs can run.

10 · AWS on demand: burst compute, database stays home

No RDS and nothing permanent with data. When prod needs more than its 3 home API pods, make burst-up makes one Spot machine in AWS that joins the home k3s cluster through a WireGuard tunnel, which the home server dials out to. The machine removes itself when idle, and make burst-down destroys everything.

Tunnel test phase 5

  • make tunnel-up / tunnel-test / tunnel-down
  • A t4g.nano endpoint; 7 of 7 checks from AWS
  • Shares the tunnel addresses with burst: one at a time

Burst phase 6

  • make burst-up, then burst-test (11 checks)
  • make burst-down after use, or after it ended itself
  • Alert BurstRecommended says when it's worth it

Costs guardrails

  • Nothing running: $0/h (the normal state)
  • Billing data lags hours: a backstop, not an exact cap
  • make guardrails-status, guardrails-reset

11 · Security layers

Each layer assumes the one above it can fail.

Edge Raspberry Pi

  • Passes TLS through; holds only the waking page's certificate
  • Sleep notices need a token (secret pi-gateway)
  • Settings file root-only (0600)
  • One magic packet per 10 s at most

Host Ubuntu

  • AppArmor profile k8s-chatbot: no mounts, no writes to /proc
  • k3s protect-kernel-defaults
  • API audit log, 7 days
  • Agent is a no-login system user in a systemd sandbox

Cluster k3s

  • Secrets encrypted at rest
  • kubeconfig mode 0600
  • Pipeline token limited to 3 namespaces
  • Priority classes protect the platform first

Pods PSA restricted

  • Non-root, read-only root filesystem
  • All capabilities dropped, no privilege escalation
  • seccomp RuntimeDefault, no service-account token
  • Requests and limits, quota per namespace

Network zero trust

  • Default deny in and out everywhere
  • Allow rules match namespace and pod label
  • Registry and API bound to localhost
  • Prometheus and helpers are not on the ingress

TLS local CA

  • cert-manager, ECDSA P-256; CA key stays in the cluster
  • HTTP → HTTPS 301, HSTS, TLS 1.1 refused
  • Postgres TLS 1.3, renewed and reloaded automatically
  • Secure, HttpOnly, signed cookies

CI Jenkins

  • Configured as code; sign-up and anonymous off
  • matrix-auth: viewer can only read and start
  • Prod approval: admin only
  • Read-only deploy key; GitHub host key pinned

Data and app chat-api

  • One database and one login per environment
  • Limits enforced by DB triggers
  • Backups daily, restore-tested weekly, off-site every 3 days
  • Rate limits, CSP, input validation; no message text in logs

AWS profile chatbot

  • Dedicated IAM user, never root; keys only in ~/.aws
  • Burst node: no SSH, WireGuard from home only
  • S3 upload key can't read or delete
  • $10 budget with a kill switch

When memory runs short priority

  • platform (1,000,000): Postgres, Ollama, Prometheus, evicted last
  • prod (100,000): prod chat-api and ui
  • default (0): dev, qa, Jenkins, helpers, evicted first
  • burst (0, never preempts): the AWS pods, on their own quota

When too many people chat ModelGate

  • Each pod streams 1 reply at a time
  • Line of 2 (prod 4), waiting up to 30 s: "you're in line"
  • Line full: "Busy right now… try again" (503) at once
  • Over 10% turned away → ChatsTurnedAway; consider burst

14 · Phases

Where the project stands. Details and test results for each step are in docs/updates.txt; problems hit along the way are in the Error Journal.

  1. 1–3Local stack: images, k3s, platform, Helm, verify, TLS with a local CA
  2. 4Jenkins CI/CD with Trivy, SBOM, approvals and automatic rollback

  4. 6AWS burst compute with Terraform: Spot node joins k3s, scraped with cloud="aws" (11 of 11)

  6. 7Sleep when idle and Wake-on-LAN through a Raspberry Pi gateway (no SQS needed); server-down alerts from the Pi

  9. 9bPublic site goes live: Netlify signs each request → Tailscale Funnel → the Pi checks the signature, allows only the public paths (chat, Pulse, Capacity, Backups view, Pipeline + trimmed logs, Be a Dev) → prod chat-api. "Back up now" stays home-only; public colour deploys capped at 6 an hour
  10. nextSecrets from a secrets manager, image signing (cosign + admission check), alerts for crash-looping pods, a gigabit cable for the server
