6. Backups: off-site copy to S3, Pulse panel and "Back up now"

Date:        9 November 2026
Commands:    make backups (install/update), backup-offsite-setup, backup-offsite-now,
             backup-admin-password (scripts/10-backups.sh); the rest as before
Why:         the nightly backups lived on the same disk as the database, so a dead disk lost
             both. And their status was only visible with kubectl.
Decided:     keep nightly backups on the server and add an off-site copy every 3 days;
             "Back up now" on Pulse needs an admin password (the site has no login).
Changed:     k8s/platform/60-backups.yaml (offsite.sh, CronJob postgres-offsite, its network
             rule), k8s/platform/65-backup-ops.yaml + backup-ops/backup_ops.py (new),
             k8s/platform/10-quotas.yaml (data quota), terraform/backups/ (new),
             app-chat (config, /api/backups endpoints, tests), helm/chatbot (BACKUP_OPS_URL,
             egress rule), app-ui/public/pulse (Backups panel, backups.js, styles),
             scripts/10-backups.sh, Makefile

Schedules (UTC):
- backup on the server: nightly 02:30, kept 14 days (unchanged);
- off-site copy to S3: every 3 days at 04:15 (days 1, 4, 7 ... of the month), kept 30 days.
  It checks the checksums, uploads the newest backup, then counts the files in S3. On
  31-day months it runs on the 31st and the 1st (one day apart);
- restore test: Sundays 03:30 (unchanged).

Pulse page, Backups panel:
- tiles for the last backup, last off-site copy and last restore test, each with OK, Failed
  or Overdue (backup older than 26 h, off-site copy older than 3.5 days, restore test older
  than 8 days) and the next run time;
- recent runs (scheduled and manual); opening one shows its log (last 300 lines), refreshed
  while it is open;
- "Back up now": asks for the admin password, then runs a backup and, when it succeeds, the
  off-site copy. The panel refreshes every 4 s while it runs, otherwise every 20 s.

How it is built:
- chat-api (the internet-facing part) still has no Kubernetes access. A small service,
  backup-ops, runs in the data namespace (python:3.13.17-alpine3.24, standard library only,
  nothing to build). Only chat-api pods may reach it (NetworkPolicy). Its Role allows only:
  read the three backup CronJobs, create and list Jobs, list pods, read pod logs. It only
  shows logs of backup-related jobs: asking for another pod's log (e.g. Postgres) gets 404.
- chat-api proxies /api/backups, /api/backups/log?job= and /api/backups/run to it.
- Password: secret backup-admin (make backup-admin-password; empty input generates one).
  Wrong guesses: 5 per 15 minutes for everyone (backup-ops) and 5 per 10 minutes per IP
  (chat-api). One backup at a time, and none within 2 minutes of the last one.
- S3 (terraform/backups, stays up like the guardrails, well under 1 cent a month): private,
  public access blocked, AES256 encryption, TLS only, versioned, copies expire after 30
  days. The uploader IAM user may only add and list files under postgres/. Its access key
  is created straight into the cluster secret offsite-s3, never on disk or in the
  Terraform state; running offsite-setup again replaces it and deletes the old one.
- The off-site job uses amazon/aws-cli:2.39.1 as uid 70 (the backup files are 0600), may
  only reach public HTTPS, and mounts the backups read-only.

Tests:       15 unit tests pass (4 new: not-connected, pass-through, input checks before any
             call, per-IP limit). make verify ENV=dev 25 of 25.
             End to end on dev: status and logs through the site; wrong password refused;
             per-IP limit kicked in; "Back up now" ran a backup (10 s) and then the off-site
             copy; a double click was refused; make backup-offsite-now uploaded 5 of 5 files,
             encrypted. Uploader key: can add and list; can't read, delete, or write
             elsewhere (checked).
Fixed:       - the old backup-ops pod kept answering for ~30 s after a restart (Python as
               PID 1 ignores SIGTERM): it now exits at once, and the Deployment uses
               Recreate, so two copies with different passwords never answer together;
             - before S3 was set up, the off-site job would hang on its missing secret until
               its 15-minute deadline: the secret is now optional and the job stops at once
               with "off-site copy is not set up yet".
Status:      done on dev. qa and prod get the panel with the next pipeline run. The admin
             password is for the owner to set (the temporary test password was removed).

5. AWS cost guardrails: 10 USD budget and kill switch

Date:        9 November 2026
Commands:    make guardrails-up, guardrails-test, guardrails-status, guardrails-reset
             (scripts/14-guardrails.sh)
Why:         a hard backstop so AWS can never run up a bill, even if a burst node is forgotten or
             the timers on it fail.
Changed:     terraform/guardrails/ (new, with lambda/kill_switch.py), scripts/14-guardrails.sh,
             Makefile, .gitignore, README.md
Decided:     alerts go to an email address kept only in terraform/guardrails/terraform.tfvars
             (gitignored, never in the repo). At 100% the kill switch terminates every EC2
             instance in every region, tagged or not: the account is used for nothing else.

What happens as spend grows (budget "qwenops-monthly-10usd", whole account, monthly):
- over 5 USD (50%) and over 8 USD (80%): email;
- forecast to pass 10 USD this month: early-warning email;
- over 10 USD (100%): email, plus two automatic actions:
  1. budget action: a deny policy (qwenops-budget-deny-create) is attached to the
     chatbot-terraform user. It blocks creating instances, Spot requests, fleets, NAT
     gateways, Elastic IPs, autoscaling groups, ECS/EKS/RDS/Lightsail/SageMaker resources.
     Deleting still works, so make burst-down can still clean up;
  2. kill switch: the budget publishes to SNS (qwenops-budget-cutoff), which runs the Lambda
     qwenops-kill-switch. In every enabled region it terminates every instance (running or
     stopped, termination protection removed first), cancels Spot requests, deletes NAT
     gateways and releases unattached Elastic IPs. EBS volumes and snapshots are kept.
- make guardrails-reset gives the user its rights back (reverses the budget action, or
  detaches the policy). If spend is still over the limit that month, it can fire again.

Security:    the budget's role may only attach or detach that one policy on that one user. The
             Lambda's role may only describe and remove EC2 compute and write its own logs
             (kept 90 days). SNS accepts messages only from AWS Budgets for this account.
Cost:        0 USD. This is the one AWS stack that stays up; everything else is destroyed after
             use. Terraform state is local and gitignored.
Limit:       AWS billing data lags by several hours, so the cut-off fires a few hours after
             spend passes 10 USD. At the burst node's ~0.05 USD an hour that is cents; the node's
             own idle (30 min) and max-lifetime (6 h) timers act first.

Result:      13 resources created. Kill switch dry run: 17 regions checked, nothing to remove,
             no errors. Spend this month 0.007 USD (forecast 0.03 USD); cut-off action STANDBY
             (armed); deny policy not attached.
Note:        the account's older "My Zero-Spend Budget" (1 USD, email only) still exists.
Fixed:       the script first said budget emails need a confirmation click; they don't. Message
             corrected.

4. Phase 6 burst compute

Date:        9 November 2026
Commands:    make burst-prepare (once, sudo), burst-up, burst-ready, burst-test, burst-down,
             burst-status (scripts/13-burst.sh)
Why:         the home server is the limit: one Ollama on 4 cores. Phase 6 adds a second machine
             in AWS only while it's needed, and destroys it afterwards.
Decided:     - what runs in AWS: extra prod chat-api pods plus their own Ollama (the model is
               the bottleneck, so API pods alone would still queue on the home Ollama);
             - start and stop: by hand, plus timers on the node that destroy it after 30 idle
               minutes or 6 hours in total;
             - machine: Spot, 4 vCPU / 8-16 GB, amd64 (the images are amd64), first c6a.xlarge only,
               now any of 10 types in 3 zones (Issue 25), 0.051-0.081 USD an hour in
               ap-south-1. Spot quota 256 vCPU, so no limit request needed.
Changed:     terraform/burst/ (new; EC2 Fleet + launch template after Issue 25), k8s/burst/ (new),
             scripts/13-burst.sh (new),
             helm/chatbot (api-burst.yaml, values, networkpolicy), scripts/06-deploy.sh,
             k8s/platform/10-quotas.yaml, k8s/platform/50-prometheus.yaml, Makefile

How it works:
- The AWS node joins the home k3s cluster as a worker over the WireGuard tunnel (home dials
  out). k3s API, flannel pod traffic and image pulls all go through the tunnel; Postgres is
  still not exposed anywhere.
- Ubuntu 24.04, not Amazon Linux: every chatbot pod requires the k8s-chatbot AppArmor
  profile, which the node loads at boot. Same k3s version as home.
- The node is tainted and labelled (qwenops.io/burst=true, qwenops.io/cloud=aws), so only
  burst pods run there.
- ollama-burst (k8s/burst/10-ollama-burst.yaml): same image and model as home, model
  downloaded on each start, same network rules (only chat-api may call it).
- chat-api-burst (Helm, prod only, 2 pods, same image tag as prod): keeps the api label, so
  the prod Service and Traefik spread chats across home and AWS pods. It connects to
  Postgres with sslmode=verify-full against the local CA.
- Images: while the tunnel is up, a read-only copy of the home registry listens on the
  tunnel address only (started and stopped by wg0). Nothing can be pushed through it.
- Join: a one-hour k3s bootstrap token, made per bring-up, deleted on burst-down.
- AWS side: own VPC, WireGuard from the home IP only, no SSH (SSM), IMDSv2 with hop limit 1
  (pods can't read the node's AWS credentials), encrypted 30 GB disk.
- burst-down turns the burst pods off, removes the node from the cluster, takes wg0 down and
  runs terraform destroy.

Already live (applied 9 November, no AWS cost):
- PriorityClass qwenops-burst and separate "burst" quotas in chatbot-prod and ai. The home
  quotas now count only pods without that class, so bursting never uses home quota.
  Checked: prod's home quota still counts its 4 pods; the burst quotas start at 0.
- Prometheus copies the node label into cloud="aws" on kubelet metrics, which the Capacity
  page uses to split local from AWS. Checked: Capacity still shows local data, AWS "not
  running".
- scripts/06-deploy.sh turns chat-api-burst on for prod while a burst node is Ready, so a
  pipeline deploy during a burst keeps the AWS pods on the new image. BURST=off forces it off.

Checks:      terraform validate, helm lint and kubectl server dry runs pass.
             burst-test will check: node Ready, labelled and tainted; ollama-burst and the
             burst pods ready on it; their Postgres connections use TLS; a real answer from
             the AWS model; nothing else on the node; burst quota in use; Capacity page shows
             the node.
Risks:       pod traffic between home and AWS rides flannel VXLAN inside WireGuard, and the join
             used a bootstrap token made with kubectl. Both worked on the first try.
Status:      done. make burst-prepare and the burst-up runs were done by hand (an automated
             permission check blocks creating AWS resources).
First run:   make burst-up stopped with exit code 141 while making the join token (a pipe into
             head under pipefail). Nothing had been created yet. Fixed with openssl rand; see
             Issue 22 in docs/capacity-journal-issues.md.
Second run:  AWS refused "terminate on shutdown" for the Spot instance (not needed for Spot;
             now set only for on-demand). Issue 23.
Third run:   AppArmor's wg-quick profile blocked starting the registry copy from PostUp; the
             script now starts it after wg0 is up. Issue 24. The node then joined, and
             ollama-burst plus both chat-api-burst pods became ready on it (so Postgres at
             home and the AWS model were reachable from AWS pods).
First test:  7 of 10 passed. AWS took the Spot machine back after 7 minutes ("no Spot
             capacity", one type in one zone). Now an EC2 Fleet over 10 instance types and
             3 zones (Spot placement score 9 of 10); burst-test checks the machine first.
             Issue 25. Cleaned up with make burst-down; next: make burst-up again.
Fleet runs:  three EC2 Fleet errors in a row ("minimum target capacity"): the provider always

             (still one machine from all types and zones). Issue 26.
Result:      11 of 11 burst-test checks passed (9 November). The fleet picked a c6i.xlarge

3. Phase 5 tunnel test: Terraform and WireGuard

Date:        9 November 2026
Commands:    make tunnel-up, make tunnel-test, make tunnel-down, make tunnel-status
             (scripts/12-tunnel.sh)
Why:         prove that something in AWS can reach the home Postgres through the tunnel, with the
             rules from update 2, before Phase 6 builds burst compute on it.
Changed:     terraform/tunnel/ (new), scripts/12-tunnel.sh (new), Makefile
Tools:       terraform 1.17.1 and wireguard-tools 1.0.20260223 installed on the server.

- AWS side (Terraform, local state, everything destroyable): its own VPC 10.100.0.0/16, one
  public subnet, one t4g.nano running Amazon Linux 2023 (arm64) in ap-south-1. Only WireGuard
  (UDP 51820) from the home public IP is let in. No SSH and no key pair; commands go through
  AWS Systems Manager. IMDSv2 only, encrypted disk. Plan: 10 resources, about 1 US cent an hour.
- WireGuard on the AWS node uses systemd-networkd (built in, no package). AWS end 10.200.0.2,
  home end 10.200.0.1. The home server dials out (keepalive 25 s), so no router port forward.
- Keys are kept outside the repo in ~/.config/qwenops-tunnel (mode 0700). The home key is kept;
  the AWS key is new on every tunnel-up and deleted on tunnel-down.
- Home wg0 needs root: tunnel-up prints the sudo lines to run (install wg0.conf, wg-quick up).
- tunnel-test runs on the AWS node and never sends a real password. It checks: the WireGuard
  handshake; ping to the home end; an app login gets as far as the password prompt (so TLS
  verify-full and pg_hba.conf passed); the superuser, another env's database, a connection
  without TLS and a wrong certificate host name are all refused.
- tunnel-down takes wg0 down, runs terraform destroy, deletes the AWS key and lists anything
  still tagged Stack=tunnel.

Result:      7 of 7 checks passed (9 November, AWS node in ap-south-1a):
             - the home end 10.200.0.1 answers ping through the tunnel;
             - an app login (chat_dev) gets as far as the password prompt, so TLS verify-full
               and pg_hba.conf both passed;
             - refused: the superuser, chat_dev asking for chat_prod's database, a connection
               without TLS, and a wrong certificate host name;
             - Postgres logs the caller as 10.200.0.2, so the tunnel address is kept and the
               rules apply to it.
             ufw did not block the tunnel traffic, and the externalIPs Service works on k3s.
Fixes:       the t4g.nano ran out of memory installing the Postgres client, and the handshake
             check needed a tool the node doesn't have. See Issue 21.
How it ran:  the first tunnel-up was blocked by an automated permission check, so it was run by
             hand, with the sudo lines for wg0; the node was then finished over SSM.
Torn down:   make tunnel-down the same day: AWS empty (instance terminated, VPC and IAM role
             deleted), home wg0 down. Only the home WireGuard key is kept for reuse.
Next:        Phase 6, burst compute (update 4).

2. Phase 5 home side: Postgres TLS and tunnel rules

Date:        9 November 2026
Command:     make db-tls (scripts/11-db-tls.sh), safe to run again
Why:         AWS burst pods (Phase 6) will reach the home Postgres through a WireGuard tunnel.
             Before that, Postgres must encrypt connections and only accept the tunnel for the
             app logins.
Changed:     k8s/platform/40-postgres.yaml, k8s/tunnel/10-postgres-tls.yaml, Makefile, README.md

- TLS: Postgres has a server certificate from the local CA (90 days, renewed 30 days early,
  new key each time). TLS 1.3 is the minimum. A small sidecar (tls-reload) checks every
  5 minutes and reloads Postgres when the certificate or pg_hba.conf changes, so no restart.
- The apps switched to TLS 1.3 on their own; their settings did not need to change.
- pg_hba.conf is now a ConfigMap. The tunnel subnet 10.200.0.0/24 gets TLS plus SCRAM, app
  logins only (chat_dev, chat_qa, chat_prod), each into its own database; the postgres
  superuser cannot log in over the tunnel. Pods in the cluster keep SCRAM. Every other
  address is rejected (before, any address could try a password).
- Service postgres-tunnel answers on the home end of the tunnel, 10.200.0.1:5432. The
  NetworkPolicy postgres-allow lets that subnet in on port 5432 only.
- AWS clients connect with sslmode=verify-full and the CA file certs/postgres-ca.crt.
- Postgres restarted once (a few seconds without a database for the apps), after a backup.
  The restart also applied the Postgres memory sizing committed in Phase 3.4 but never
  deployed (768Mi limit, 256MB shared_buffers).

Result:      9 of 9 db-tls checks passed; make verify ENV=dev passed 25 of 25.
