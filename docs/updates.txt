Date:        10 November 2026
Commands:    make public-chat-setup, public-chat-netlify, public-chat-secret, public-chat-test,
             public-chat-status, public-chat-off (scripts/21-public-chat.sh)
Why:         the public (Netlify) site was a static copy. Now visitors use the real thing: chat with
             saved history, Pulse, Capacity, the Backups panel (view only), the Pipeline page with
             logs, and Be a Dev, without opening the router.
Changed:     app-chat/app/main.py, config.py, schema.sql (+ tests), ci/pipeline-events (public log

             Be a Dev, Pulse, Capacity, Backups panel), Makefile, README, Architecture page

The path:
  visitor → Netlify site (/api/... and /theme.json; Netlify signs each request with
  QWENOPS_PROXY_SECRET) → Tailscale Funnel (public HTTPS, opened from home) → Pi nginx
  127.0.0.1:8090 → prod chat-api as chatbot.local.

On the Pi (nginx with its JavaScript module):
- checks Netlify's signature (HS256, issuer netlify, not expired); anything else gets 403, so the
  Funnel address can't be used directly;
- only the public paths; "Back up now" (/api/backups/run), metrics and anything else get 404;
- flood limits per visitor (chat 12 a minute, pages 180 a minute), at most 6 replies streaming;
- adds the edge secret and the visitor's address; checks prod's certificate against the home CA;
- server asleep: /api/status and /api/wake go to the waker, which wakes it; the rest answer
  "waking up, try again".

In chat-api, a request is public only with the right edge secret. Public visitors get the home
rules (10 messages a minute, saved history, 512-token replies), and:
- "Back up now" is refused (404), as a second guard behind the Pi;
- at most 6 colour deploys an hour from the public site in total (plus 1 per visitor every 5 min);
  Be a Dev there changes prod's colour, and the public site shows prod's live colour;
- pipeline logs are trimmed by pipeline-events: private IPs, MAC addresses, internal service names
  and home paths blanked; the security-scan stage's log isn't shown;
- rate limits use the visitor's real address, not the Pi's.

History rule changed for everyone (one database): at 50 users, a new user replaces the FIRST user
created, whose chats are deleted (before: the 51st user was refused and chatted as a guest). Asked
for on 10 November; the risk that a flood of new visitors removes everyone's history, including
the family's, was explained and accepted.

Problems weighed before building (explained to the owner): strangers redeploying prod's web pods
(capped), logs showing internals and known weaknesses (trimmed), Pulse showing when the house is
using the server or asleep, guessing the backup password (button hidden), history wiped by floods
(accepted), long replies cut by Netlify's ~26 s proxy limit (to be measured), load and power (the
server will sleep less), and storing strangers' chats at home and in the S3 backups.

Result so far: chat-api tests 29 passed (new: only the right secret makes a request public; the

12. Server-down alerts from the Pi

Date:        9 November 2026
Commands:    make pi-gateway (update the Pi), make pi-quiet MINUTES=30 (planned work),
             make pi-status (now shows what the watcher sees), make alert-test (sudo: sleep
             5 min without telling the Pi, to test the alert end to end)
Why:         the alerts (update 7) run on the server, so if the server crashes, loses power or
             its cable comes out, nothing can tell you. Now that it sleeps and wakes, "down"
             can also be normal, so the watcher must tell a planned sleep from a failure.
Changed:     pi/gateway/waker.py (watcher, alerts, LAN port 8082), pi/setup.sh (settings file
             root-only, state kept across restarts), scripts/18-pi-gateway.sh (token, topic,
             checks, quiet), scripts/17-sleep.sh (tells the Pi before sleeping, alert-test),
             Makefile

How it works:
- Every 30 s the Pi checks whether the server accepts a connection on its HTTPS port.
- Before every planned sleep (idle sleep, make sleep-now, make wol-test) the server tells the
  Pi "asleep until <time>, reason" on the Pi's LAN port 8082, with a shared token. The token
  is made once and kept in the cluster (secret pi-gateway, namespace monitoring) and in the
  Pi's root-only settings file; a notice with a wrong token gets 401. The Pi saves the notice,
  so a Pi restart during a planned sleep doesn't turn it into an alarm.
- Alerts go straight from the Pi to your ntfy topic (the same one as update 7), urgent:
    "Server is down (not asleep)"     no answer for 3 minutes, and no sleep announced
                                      (crash, power cut, cable, network);
    "Server didn't wake on schedule"  still down 10 minutes after the announced wake time;
    "Server didn't wake after a visit" the Pi sent the wake packet for a visitor 5 minutes
                                      ago and the server still doesn't answer;
    "Server is back"                  normal priority, with roughly how long it was down.
- One alert per outage; short blips under 3 minutes (a Wi-Fi hiccup) stay quiet.
- make pi-quiet MINUTES=30 silences "down" alerts for planned work (reboot, BIOS).
- GET http://<pi>:8082/watch shows what the watcher sees (up/down, for how long, announced
  sleep, whether it can alert); no secrets in it.

Tests:       the decision logic, with a simulated clock: crash -> alert after 3 min, then
             "back"; 60 s blip -> nothing; announced sleep that wakes on time -> nothing;
             announced sleep that never wakes -> one alert 10 min after the wake time; a
             visit's wake packet with the server staying down -> alert 5 min later. All pass.
             Scripts: syntax checks pass, waker passes ruff. make pi-test now has 14 checks
             (new: watcher sees the server up, can alert the phone, refuses notices without
             the token).
Real test:   after make pi-gateway (14 of 14 checks) and make sleep-setup, make alert-test slept
             without telling the Pi (Pi log, IST):
               20:32:05  sleep notice with a wrong token refused (pi-test check)
               21:04:24  server down, no sleep announced
               21:07:34  alert "Server is down (not asleep)", priority 5 (3 min 10 s later)
               21:08:38  alert "Server is back", priority 3
             and the owner got both on the phone. Announced sleeps (make sleep-now) gave no alert.
             A first alert-test run woke after about 30 s by itself, before any alert (Issue 42).
Mistake:     the first version of the "visit" test case stopped one step before the expected
             alert time and failed; the watcher was right, the test window was extended.
Status:      done.

11. Phase 7: Raspberry Pi gateway, wake on visit

Date:        9 November 2026
Commands:    make pi-gateway (install/update; asks the Pi's sudo password once), pi-test,
             pi-simulate (Pi's sudo password), pi-status (scripts/18-pi-gateway.sh; Pi side
             in pi/setup.sh, pi/gateway/waker.py, pi/gateway/waking.html; certificate in
             k8s/edge/10-pi-gateway-tls.yaml)
Why:         a sleeping server can't wake itself when someone visits, and the site lives on it.
             An always-on Raspberry Pi stands in for it.
Hardware:    Raspberry Pi 3 Model B+, Debian 13 (trixie) 64-bit, Wi-Fi, 192.168.1.104 (user rasppi).

How it works:
- The Pi announces chatbot.local, dev., qa. and jenkins.chatbot.local on the Wi-Fi (mDNS),
  pointing at itself. This also fixed phone access (update 9).
- nginx on the Pi passes every connection straight through to the server (TCP, TLS untouched:
  the server's own certificates are used end to end).
- If the server doesn't answer within 1 s (asleep), nginx falls back to a local "waking up"
  site with its own certificate from the home CA (1 year, from cert-manager):
    1. the page opening sends the magic packet (at most one per 10 s), and the page re-sends
       every 20 s in case one was missed;
    2. the page shows "The server was asleep. Waking it up..." with a progress bar;
    3. it asks the Pi every 3 s; the Pi checks the server's /api/readyz over HTTPS against the
       home CA (that endpoint doesn't count as activity, so the Pi never keeps the server awake);
    4. on "ready" the page reloads and, on a fresh connection, gets the real site.
- The chat page's own /api/wake and /api/status calls are answered by the Pi while the server
  sleeps, so an already-open chat page waits correctly too. Other API calls get 503
  "The server is waking up".
- Security: the Pi's private key is only in /etc/qwenops-gateway (readable by nginx); the copy
  used for the install is deleted right after. The waker runs as a DynamicUser with a read-only
  system; the name announcer as system user qwenops (group netdev, no login).

Tests:       make pi-test (11 checks): dev and prod through the Pi reach the server, TLS passes
             through untouched, http redirects to https, the four names announced as the Pi,
             nginx, waker and announcer running, waker sees the server as ready.
             make pi-simulate (pass-through pointed at an unused address): waking page with a
             trusted certificate, connection closed after each answer, http redirect,
             /api/wake accepted, /api/status answers, API calls get 503, magic packet sent.
             Real: the server woken from sleep by opening the site from an ntfy notification on
             the phone, and from the Windows laptop; the site loaded by itself after waking.
Fixed:       names not really announced (Issue 37), reload loop after waking (Issue 38),
             Windows going around the Pi (Issue 39).
Needs:       fixed addresses (DHCP reservations) for the server (192.168.1.101) and the Pi
             (192.168.1.104); if they change, re-run make pi-gateway. Clients must find .local
             names (iPhone, Mac, Windows 10/11, Android 12+) and trust the home CA
             (make lan-share-ca); Windows hosts-file entries must point at the Pi or be removed.

10. Phase 7: sleep when idle, Wake-on-LAN, IST times

Date:        9 November 2026
Commands:    make sleep-setup (sudo), sleep-status, sleep-now [MINUTES=n] (sudo), stay-awake,
             allow-sleep, wol-test (sudo) (scripts/17-sleep.sh)
Why:         save power when nobody is using the server.
Hardware:    Dell OptiPlex 3020, Realtek network card (r8169), supports suspend to RAM (S3) and
             a wake-up timer in its clock chip. BIOS: Wake on LAN = LAN Only, Deep Sleep
             Control = Disabled, Block Sleep off, Auto On Time off (AC Recovery = Last Power
             State recommended).

How it works:
- Wake-on-LAN (magic packet) is switched on in the card at boot and before every sleep.
- Every 5 minutes an idle check decides. The server sleeps after 30 minutes with none of:
  app traffic (chats, Pulse, any /api call except health probes), a Jenkins build, a backup
  job, an AWS burst node, an SSH session (VS Code Remote counts), the stay-awake switch, or
  the backup window.
- All times are in IST (SLEEP_TZ=Asia/Kolkata in /etc/qwenops-sleep.conf). The backup jobs
  run on UTC, so the server stays awake 07:45-10:00 IST and wakes itself at 07:50 IST for the
  08:00 backup, the Sunday 09:00 restore test and the 09:45 off-site copy.
- Before sleeping it sends a quiet ntfy note ("Server sleeping ... wakes itself at 07:50 IST").
- It wakes by: the Pi gateway when someone opens the site (update 11), a Wake-on-LAN phone app
  (MAC f8:bc:12:89:34:5f, broadcast 192.168.1.255, port 9), or its own timer.
- make sleep-now MINUTES=2 sleeps and wakes itself after 2 minutes, for testing.
- make wol-test tests each link: A the card's setting, B a packet from the Pi reaching the
  server's cable while awake, C a real sleep woken by the Pi (7-minute fallback timer).

Tests:       dry runs of the idle check: awake with reasons (SSH, app requests), "idle 0 of 30
             min", and "sleeping; wakes itself at Tue 07:50 IST" after 31 idle minutes.
             Timer wake: slept 19:47:51, back 19:49:49 IST (2 minutes). make wol-test:
             A Wake-on: g, ACPI wake enabled; B magic packet from the Pi seen on enp2s0;
             C woken by the Pi after 46 s (fallback 420 s).
Fixed:       the broadcast address read as "100" (Issue 36); octal time comparison, dry-run
             kubeconfig and draft paths (Issue 40).
Limits:      while asleep nothing runs: no alerts, no Jenkins builds (they run once it is
             awake), no backups outside the window. After waking, k3s needs 1-2 minutes before
             the site answers. The network link runs at 100 Mb/s (Issue 41).

8. Overload protection: "busy" fast, prod first

Date:        9 November 2026
Why:         second layer of the "what happens at 100%" plan. Before, extra chats queued behind
             Ollama (2 replies at a time) until they timed out after 120 s, with no word to the
             user; and dev, qa and Jenkins competed with prod for memory on equal terms.
Changed:     app-chat (ModelGate in main.py, config, 3 tests), app-ui/public/chat.js,
             helm/chatbot (api.chat values, priorityClassName for prod API and UI),
             k8s/platform/10-quotas.yaml (priority classes), 30-ollama.yaml, 40-postgres.yaml,
             50-prometheus.yaml (platform priority, ChatsTurnedAway alert)

How it works, step by step:
- Think of each chat-api pod as a counter with one clerk (the "slot") and a few chairs (the
  "line"). The clerk serves one person at a time: that is one reply streaming from the model.
- 1. A chat arrives. If the clerk is busy AND every chair is taken, the pod answers at once:
     "Busy right now ... Try again in a moment" (HTTP 503, Retry-After 15 s). Nothing else
     runs: no database lookup, no model call. This takes about 0.2 s.
- 2. Otherwise the reply stream opens. If the clerk is free, the reply starts right away.
- 3. If the clerk is busy but a chair is free, the person sits down and the page shows
     "Busy right now, you're in line (N ahead)...".
- 4. When the clerk finishes a reply, the next person in line is served, and the "in line"
     note is replaced by the reply's first words.
- 5. If someone has waited 30 s and still isn't served, they get the same "busy, try again"
     message, and their chair is freed.
- 6. If someone closes the page while waiting or while their reply streams, their chair or
     the clerk is freed at once for the next person (the slot is always given back).
- Example on dev (1 clerk, 2 chairs), 6 chats sent at the same moment: the 1st streams at
  once (5 s), the 2nd and 3rd wait and are answered (9 s and 15 s), the 4th, 5th and 6th get
  "busy" in 0.2 s. Prod has 2-3 pods, each with 1 clerk and 4 chairs, so up to 3 replies
  stream at once and up to 12 people can wait.
- Why so few clerks: dev, qa and prod all talk to the same Ollama, which writes 2 replies at a
  time on the home server's 4 cores. More clerks would only build a hidden queue inside Ollama,
  where people wait up to 2 minutes with no message. The line makes that wait visible and short.
- What you see when it happens: the Pulse page counts "busy" chats (chat_requests_total with
  outcome="busy") and people waiting (chat_waiting); if over 10% of prod chats are turned away
  for 5 minutes, the ChatsTurnedAway alert reaches your phone and suggests make burst-up.
  A burst node adds its own Ollama and 2 more pods, each with its own clerk and chairs.
- Under memory pressure (the other half of this update): the kubelet evicts lower-priority pods
  first, so dev, qa and Jenkins go before prod, and prod goes before Postgres, Ollama and
  Prometheus. Once the pressure is gone, the evicted pods are started again by their
  Deployments.
- Settings: helm values api.chat (slots, queue, waitSeconds), per environment. Changing them
  is a normal deploy; no code change.

Fail fast (chat-api, per pod):
- 1 reply streamed at a time per pod, a line of 2 (dev, qa) or 4 (prod), 30 s wait at most.
  All environments share one Ollama, so the totals stay close to its 2 replies at a time.
- In line: the page shows "Busy right now, you're in line (N ahead)..." until the reply starts.
- Line full: "Busy right now: lots of people are chatting. Try again in a moment." at once
  (HTTP 503, Retry-After 15 s, before any database or model work); after 30 s in line, the
  same message.
- The slot is taken inside the stream and always given back, even if the page is closed
  while waiting.
- New metrics: outcome="busy" in chat_requests_total, and chat_waiting.
- New alert ChatsTurnedAway (warning): over 10% of prod chats get "busy" for 5 minutes;
  suggests make burst-up. 12 alert rules now.

Prod first (priority classes):

- qwenops-prod (100,000): prod chat-api and UI.
- dev, qa, Jenkins and backup jobs stay at the default (0): under memory pressure the kubelet
  evicts them first (among pods using more than they asked for), and a prod pod that doesn't
  fit may push them off the node. Burst pods keep qwenops-burst. The home quotas still count
  every pod except burst ones.

- Alertmanager groups alerts by name (waits 30 s, so alerts that fire together arrive as one

  namespace. On ntfy.sh anyone with the name can read it, so it must stay private.
- Network rules: only Prometheus may reach Alertmanager, only Alertmanager may reach the
  bridge, and the bridge may only reach public HTTPS.

  2 min), ChatsFailing (> 5% of prod chats error, 5 min), ServerErrors (> 5% of prod

  > 8 days), BackupOpsDown (10 min), BurstNodeRunningLong (AWS node up > 4 h).
- Home numbers leave out AWS burst nodes (cloud!="aws"); burst pods don't count toward the
  3/3 home limit.
